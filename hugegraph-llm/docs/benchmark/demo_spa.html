0 · 一句话开场

给面试官的第一句话要精准、不啰嗦。

开口说：「我为 HugeGraph-LLM 的 GraphRAG 能力做了一套轻量、可复现、中文友好的评测系统，覆盖图抽取、召回、答案三个环节共 21 个指标，能跑离线评测也能接 LLM-Judge，并且能保存 baseline、做版本对比、定位到具体退化样例——完整对应上游 Issue #75 的 12 项验收，全部满足并超额。」

三个钩子（挑一个展开）

① GraphRAG 特有

通用 RAG 框架（RAGAS/DeepEval）只评检索和生成，不评图抽取。我补齐了 entity/triple/property/schema 共 9 个抽取指标——这是 GraphRAG 区别于普通 RAG 的核心。

② 不强依赖 LLM

Issue 明确要求"基础评测不强依赖外部 LLM"。我做的指标里 14 个纯离线，加 --offline 一行命令跑完，不调任何 API。

③ 能定位退化样例

不只给平均分。改完代码 compare 一下，直接告诉你 哪几个样本退化了、退化了多少，附在每个指标上的 delta。

1 · 为什么需要这个 benchmark

背景痛点（Issue 原话转述）：「修改图抽取流程、prompt、召回策略、rerank 逻辑、上下文构造或回答生成逻辑后，很难判断效果是否真的变好，也不容易发现具体退化样例。」

一句话价值主张

把"我改了代码 → 效果到底变好没"这个本来靠人眼读输出、靠感觉判断的过程，变成可量化、可对比、可定位的工程动作。

Issue 的硬约束（这些都是我设计时的红线）

约束含义我怎么落地
轻量不引入重框架不依赖 RAGAS/DeepEval，自建内核，纯 stdlib + jieba/opencc/rouge_score
可复现同输入同结果离线确定性 + baseline 全量持久化 + git_commit/timestamp/seed 元数据
中文友好中文场景不能掉分全角半角统一、繁简转换、中文标点、jieba 分词、双语 Judge prompt
不强依赖 LLM基础评测离线可跑21 指标中 14 个纯离线；--offline 跳过所有 LLM-Judge
覆盖抽取+召回GraphRAG 两端都要9 抽取 + 6 召回（+ 6 答案超额项）

调研结论（验收项 #1）

框架借鉴点不直接用的原因
RAGAS指标定义、prompt 风格核心指标强依赖 LLM-as-Judge；英文为主；无图抽取维度
DeepEvalCI/CD 友好pytest 测试用例范式，非 CLI 批跑；无图抽取维度
ARES无监督思路研究导向，工程化弱；指标少
TruLensfeedback 机制定位是运行时追踪，非批跑 benchmark
GraphRAG-Bench任务难度分层、JSON 自愈解析评端到端 pipeline，非组件级；无抽取质量细分

结论：借鉴设计、自建轻量内核。理由：上述框架都不评测"图抽取质量"（vertex/edge/property/schema），而这正是 GraphRAG 区别于普通 RAG 的核心。

3 · 系统架构与逻辑闭环

讲清楚"数据怎么进来、指标怎么算、结果怎么存怎么比"。

模块结构

hugegraph_llm/benchmark/
├── cli.py                 # run / compare 两个子命令入口
├── metrics/
│   ├── extraction/  (9)   # entity/triple/property/schema/syntax/structural/conflict/temporal/graph_structure
│   ├── retrieval/   (6)   # recall_at_k/hit_at_k/mrr/context_precision/context_relevancy/evidence_recall
│   └── answer/      (6)   # token_f1/exact_match/rouge_l/answer_correctness/faithfulness/coverage
├── runners/               # extraction / retrieval / ablation / base
├── baseline/              # store + compare
├── reporters/             # json_reporter + markdown_reporter
├── llm_judge/             # OpenAI-compatible client + prompts(双语)
├── datasets/              # 8 个公开数据集转换器
├── utils/normalize.py     # 中英文归一化管线
└── data/samples/          # 6 组内置样例(含中文汽车手册)

核心数据流（一个样本的生命周期）

输入 JSON→ Runner 逐样本→ 逐 metric 计算→ SampleResult→ 聚合 overall + by_type→ BenchmarkResult→ 报告 / baseline

三层隔离（鲁棒性核心）

层级失败时行为实现
样本级单样本抛异常 → 该样本空结果，其他样本继续_run_samples_concurrent_errors
指标级单 metric 失败 → 该 metric 返回 {}，同样本其他 metric 继续_run_metric_safe
LLM 级API 抖动 → 2 次指数退避重试，全失败降级retry_llm_call
为什么要强调这个：「真实数据是脏的、LLM 会抽风、API 会抖。如果一条脏数据能让整个评测崩掉，这个 benchmark 就没法用。所以我在样本、指标、LLM 三层都做了隔离——这是工程经验和学生项目的分水岭。」

5 · 图抽取指标（9 个）

GraphRAG 区别于普通 RAG 的核心。挑 2–3 个讲透原理，其余过一遍。

指标评什么类型对照 Issue mermaid
syntax_validityLLM 输出 JSON 可解析率 + 入库成功率离线Syntax Validity
schema_validity类型约束通过率 / 必填属性填充率 / 非法边比例离线Schema Validity
structural_integrity孤立点 / 悬挂边 / 重复三元组离线结构完整性
entity_f1实体 P/R/F1（对照 gold vertices）离线Entity Quality
triple_f1三元组 P/R/F1（对照 gold edges）离线Relation Quality
property_f1属性 P/R/F1离线属性质量
conflict_detection实体/关系冲突检测LLMClaim Quality
temporal_validity时序一致性（事件先后矛盾）LLMClaim Quality
graph_structure密度 / 聚类系数 / 连通性离线对标 GraphRAG-Bench indexing

重点讲：entity_f1 的原理

匹配键：把每个 vertex 归一化成 (label, name) 二元组。不是字符串模糊匹配，是集合运算。

pred_keys = { normalize(label,name) for v in candidate }
ref_keys  = { normalize(label,name) for v in gold }
tp = |pred_keys ∩ ref_keys|
precision = tp / |pred_keys|
recall    = tp / |ref_keys|
f1        = 2*P*R/(P+R)

归一化用 normalize_answer（见第 8 节），消除大小写/全半角/繁简/标点差异。空 key 会被丢弃，防止脏 vertex 污染分母。

话术：「entity_f1 不是简单的'字符串相等'。我把每个实体归一化成 (label,name) 集合元素，做集合交并——这样'宝马'和'寶馬'、'BMW'和'bmw'不会算成两个不同实体。这是中文场景必须做的。」

6 · 召回指标（6 个）

回答两个问题：该召回的召回了没？召回的内容有效吗？

指标公式/含义类型
recall_at_k各 K 截断下 |top_k ∩ gold| / |gold|离线
hit_at_khit_any@K（至少命中一个）/ hit_all@K（全部命中）离线
mrr第一个相关文档的倒数排名 1/rank离线
context_precision检索结果中相关内容的精确率LLM
context_relevancy检索上下文与问题的相关度LLM
evidence_recall_llmLLM 判定期望证据是否被覆盖（柔性）LLM

重点讲：recall@k 的原理

for k in [1,5,10,20]:
    top_k = { normalize_doc_id(d) for d in retrieved[:k] }
    recall@k = |top_k ∩ gold_set| / |gold_set|

关键：用 normalize_doc_id（strip+lower）归一化文档 ID，防止 "doc_1 " vs "DOC_1" 假阴性。gold 为空时 recall=0（而非除零）。

真实数字：三个多跳 QA 数据集召回对比（doc_id 已修正为 title）

数据集nrecall@1recall@5recall@10hit_any@5mrr
hotpotqa1000.0600.4901.0000.7700.368
musique500.0300.1600.4500.3200.200
2wikimultihopqa1000.0850.5121.0000.8400.465
话术：「musique 最难——recall@5 只有 0.16、mrr 0.20，因为它需要 2-4 跳推理，单跳召回很难命中所有 gold。hotpotqa/2wiki 是 distractor setting（gold 一定在候选里），所以 recall@10=1.0，真正区分度在 recall@1 和 mrr。这个对比本身就是 benchmark 的价值：能量化不同数据集的难度差异。」

✓ 数据已修正 此前这些数据集的 gold_doc_ids 装的是整段文本而非 title，导致 recall/mrr 是靠脆弱的全文精确匹配算出来的（数字虚高/失真）。现已修正下载源（HuggingFace 镜像）+ postprocess，gold_doc_ids 存真正的 title（如 'Scott Derrickson'），recall/mrr 严格可信。GraphRAG-Bench 不在此列——它不支持 doc_id 级 rank 评测（见第 17 节）。

⚠ 注意 graphrag_bench_medical 的 recall 全是 0。我在做的时候发现这不是召回真的差，而是该数据集 sample 的 metadata 里 gold_doc_ids/retrieved_doc_ids 字段为空（数据转换时没填进去）。详见第 17 节「待商榷点」。演示时不要拿 medical 当"召回质量差"的例子。

7 · 答案指标（6 个，超额）

Issue 没要求，但 GraphRAG 的"生成"端不评就缺一截。用于 ablation 模式对比 4 种检索策略。

指标评什么类型

ablation：4 种检索策略对比

同一条问题，用 4 种召回分别生成答案，用答案指标打分：

变体含义
raw无 RAG 基线
vector_only仅向量召回
graph_only仅图召回

话术：「这 4 个变体能回答 GraphRAG 的核心问题——图召回到底比纯向量召回好在哪、好在哪种问题上。配合难度分层，能精确看到'graph_vector 在 Fact Retrieval 上赢、在 Summarization 上反而输'。」

① 归一化管线（中文友好的关键）

# 英文路径
空格分词  →  小写
# 共同
去标点(含中文标点 ，。！？、；：""（）【】)  →  去冠词(a/an/the,仅英文)  →  折叠空白

真实例子：同一实体在三个抽取版本里的不同写法（car33 场景）

话术：「归一化是中文评测的命门。我用三个真实例子演示：全角半角、大小写、繁简体、空格这些差异我们的管线全部能消掉——寶馬５系 归一成 宝马5系，ＢＭＷ 归一成 bmw。我做这套的时候还顺手发现 opencc 没装导致繁简静默失效，已经修掉并验证了——当场用真实输出证明归一化在 work，比空讲原理有说服力得多。」

③ 离线 vs LLM 指标的边界

离线（14 个）

纯计算，无网络、无随机性。--offline 模式只跑这些。包括所有 P/R/F1、recall@k、schema/syntax 校验、graph_structure。

LLM-Judge（7 个）

需要语义判断的：faithfulness、context_precision、coverage 等。固定 temperature=0, seed=42 保证可复现。

话术：「这个分层是 Issue 的硬要求——基础评测不能强依赖外部 LLM。我把指标分成两类：能用集合运算和规则算的，全部离线；只有需要语义判断的才用 LLM，而且 LLM 那部分也是可选的，--offline 一键跳过。」

17 · ⚠ 过程中发现的待商榷点

诚实比完美更重要。做这套 SPA 时我核对了真实数据，发现两处指标/数据不一致，明天是否处理想听你意见，不急着改。

待商榷点 #1：GraphRAG-Bench (medical/novel) 不支持 doc_id 级 rank 评测

现象：medical/novel 的 recall@k、mrr 全为 0。

根因（已查明）：GraphRAG-Bench 的 Questions 只有改写过的 evidence 文本（非原文 span，在 corpus 里精确匹配 0/50），没有 gold document ID / chunk ID / question-to-chunk relevance judgments；Corpus 是整篇 105 万字符的长文档，无官方 chunk 切分。因此该数据集从设计上就不支持严格可复现的 ID-based Recall@K / MRR / nDCG。

结论：数据集局限不是 bug，是数据集定位决定的。GraphRAG-Bench 官方用 Context Relevancy + LLM 语义归因的 Evidence Recall 评检索，不评 chunk 排名。「不支持严格 doc/chunk 排名评测」是对的；「完全不评检索」是错的。

处理：演示时 GraphRAG-Bench 降优先级，召回 rank 演示只用 HotpotQA/MuSiQue/2Wiki（天然带 title 作为 doc_id）。GraphRAG-Bench 若要用，只看 context_relevancy / evidence_recall_llm。

已修复：HotpotQA/MuSiQue/2Wiki 的 doc_id ✓

原问题：这三家的 eval_ready 中间数据里，gold_doc_ids 装的是整段文本（698 字符）而非 title，normalize_doc_id 靠脆弱的全文精确匹配，recall/mrr 数字失真。根因是下载源（CMU）已失效（502），旧数据由过期转换器生成。

已处理：① 把下载源切到 HuggingFace 镜像（hotpotqa/2wiki parquet、musique jsonl）；② 新增 postprocess 把 HF 的 struct-of-arrays / JSON-string 格式转回转换器期望的 list-of-dicts；③ 重新生成数据 + baseline，gold_doc_ids 现在是真正的 title（如 'Scott Derrickson'），recall/mrr 严格可信。

待商榷点 #2：car33 的 json_parse_rate=0 与 load_to_db_success=0

现象：car33 各版本 baseline 里 json_parse_rate 和 load_to_db_success 都是 0，但 entity_f1/triple_f1 却有非零值。

排查：syntax_validity 需要 candidate 带 raw_responses + parse_results 字段才计算；car33 的 candidate JSON 只带了已解析好的 vertex/edge 结构，没有原始 raw_responses → parse_rate=0 是"缺字段"而非"真解析失败"。F1 用的是已填好的结构，所以非零。

结论：指标/数据口径不一致json_parse_rate=0 会被误读成"抽取全失败"。

建议：① 在 candidate 数据里补 raw_responses；② 或让 syntax_validity 在缺字段时返回 null/未评估 而非 0；③ 演示时口头说明这个 0 不代表真实失败。

待商榷点 #3：opencc 繁简转换静默失效 ✓ 已修复

现象：归一化文档宣传"繁→简(opencc)"，但用 normalize_answer('寶馬５系','zh') 实测输出 寶馬5系——繁体"寶馬"未被转成"宝马"。

排查：opencc 是可选依赖（try: from opencc import OpenCC），当前 .venv 未安装，import 失败被 except 静默跳过，繁简转换整段不执行，但无任何告警。

已处理：安装 opencc-python-reimplemented==0.1.7，实测 寶馬５系 → 宝马5系 繁简转换正常生效。遗留动作（待你确认）：把该依赖固化进 pyproject.toml 的 benchmark extras，并在缺失时打印 warning 而非完全静默——避免他人在新环境重复踩坑。

设计层面的反思（非 bug，供讨论）

  • oracle sanity 容易被误读：extraction 的 oracle 测试（candidate=gold 复制）只能证明"指标链路通"，但 F1=1.0 容易被误读成"抽取效果满分"。文档已注明，但报告里可加 test_type=oracle 标签更醒目。
  • Provenance Quality 未实现：Issue mermaid 里的 source span / doc attribution 没做。Issue 自己写明"后续扩展"，但演示时要主动说"这一项是 roadmap"，别藏着。
  • ablation 的 controlled answer：验证用的人工构造答案，非真实 pipeline 产物。已注明，但报告标题可强化"controlled"字样。

面试官可能的追问 & 回答

Q: 为什么不直接用 RAGAS？核心指标强依赖 LLM、英文为主、且无图抽取维度——而图抽取正是 GraphRAG 的核心。我借鉴了它的指标定义和 prompt 风格，但自建轻量内核。
Q: LLM-Judge 结果可信吗？不可全信，所以我把离线和 LLM 分层。离线指标（P/R/F1、recall@k）是客观的；LLM 指标固定 temperature=0/seed=42 保证可复现，且作为补充而非唯一依据。
Q: 并发会不会破坏可复现？不会。BaseMetric 无状态、_errors 加 Lock、result.samples 按原序。相同输入+相同并发度=相同 per-sample 值。
Q: 怎么扩展到新数据集？写个转换函数做字段映射，不动核心代码。已支持 8 个公开数据集。
Q: medical recall 全 0 怎么解释？（见第 17 节）—— 这是数据转换没填 doc_ids，不是召回真差。我已定位，等修。
